# Phase 3: React Native and Hermes Validation Plan

## Goal and constraints

Create a small consumer app that exercises the published Nexora build under Hermes and Metro. Keep the existing Vitest suite for deterministic library logic, and use the React Native app for behavior that depends on native networking, Hermes globals, and Metro resolution.

This is a plan only. No React Native app has been created or run, and no compatibility claim should be made until the stated native builds have been tested.

## Recommended fixture

Use a bare React Native Community CLI app with Hermes enabled. A bare app keeps the native networking stack and build configuration visible and avoids introducing an Expo runtime as an additional variable.

Proposed layout:

```text
react-native-fixture/
  android/
  ios/
  App.tsx
  app.json
  index.js
  metro.config.js
  package.json
  README.md
  src/
    cases/
      auth-redirect.ts
      cancellation.ts
      cache-isolation.ts
      clone-fallback.ts
    test-server.ts
```

Keep the fixture independent of Nexora's source tree: consume a packed npm tarball of the built package. This checks the same package boundary and entry points that downstream Metro consumers use.

### Minimum dependencies

- `react` and `react-native`, pinned to the selected React Native release and its matching React version.
- The React Native Community CLI and its platform packages, as generated by the matching bare-app template.
- `typescript` and `@types/react` only if the fixture is written in TypeScript.
- No extra HTTP client and no test framework are required for an initial fixture. Use a small in-app test runner and visible pass/fail results so a test can run on a simulator or physical device. Add device automation only if manual runs prove insufficient.

Use the template's default Hermes configuration and verify the actual build is using Hermes; do not use remote JavaScript debugging as a substitute for Hermes execution.

## React Native version policy

Start with React Native 0.86 as the proposed minimum and test a current release as the second matrix point. At the time of the prior planning review, React Native 0.87 and 0.88 were active while 0.86 was at end-of-cycle. Thus 0.86 offers a broader compatibility floor, while 0.87 is the more conservative choice if the project intends to support only actively maintained releases.

Metro package-exports support is enabled by default from Metro 0.82, corresponding to React Native 0.79 and later. The proposed 0.86 floor is above that boundary, but package resolution still must be tested with the exact Metro version installed by each selected React Native release.

Before declaring a support policy, confirm the React Native release lifecycle and Hermes version paired with each pinned React Native version. Record exact versions in fixture documentation and validation results. If support is intended to mean actively maintained releases only, raise the floor to 0.87 rather than treating an end-of-cycle release as supported.

## Package-through-Metro workflow

1. Run Nexora's normal build and inspect the package contents using `npm pack --dry-run`.
2. Resolve packaging problems before using the package as a fixture input. In the inspected build, `dist` contained ten compiled `*.test.js` files, while the package `files` list includes both `dist` and `src`. The fixture should consume only the package's public build, not source aliases or test files. Exclude test artifacts through the eventual build/package configuration as appropriate; do not hide this issue with a Metro alias.
3. Produce the tarball into the fixture directory with `npm pack --pack-destination .\\react-native-fixture`.
4. Install that tarball in the fixture using a local file dependency (for example, `npm install .\\nexora-0.1.0.tgz` from the fixture directory). Keep the generated lockfile so the React Native and Metro versions are reproducible.
5. Import Nexora through its package name from `App.tsx` or a fixture module. Do not import `src/` or `dist/` by relative path; the package root import exercises `package.json` exports.
6. Start Metro from the fixture root and build/run the app with the standard React Native CLI commands. Verify both a development bundle and a release bundle resolve the ESM export.
7. Repeat after changing the Nexora package: rebuild, repack, reinstall the tarball, clear Metro's cache if resolution appears stale, and rerun the matrix.

The current package declares ESM and an `exports` map to `dist/index.js`, but the package lock's root metadata does not match `package.json` (the observed lock root says version `1.0.0` / ISC while the manifest says `0.1.0` / MIT). Reconcile that metadata before relying on reproducible fixture installs. Treat package contents and lockfile consistency as prerequisites, not as evidence of React Native compatibility.

## Test design

Build a minimal controllable HTTPS test service with disposable credentials and endpoints for delayed responses, redirects, cookies, retryable statuses, and response streaming. Make the service reachable from devices over the LAN or a test environment; a device's `localhost` is not the development machine. Use a trusted certificate configured for the test device rather than weakening TLS checks. Do not use real user credentials.

Use unique request IDs in the fixture server's logs so cancellation, retries, and account switching can be correlated with the app output. Make each test report the React Native version, platform, build mode, and pass/fail result.

## Local checks versus native checks

### Local Node/Windows-capable checks

These are useful package and unit checks, but they do not establish native compatibility:

```powershell
npm run check
npm run build
npm pack --dry-run
```

On a Windows machine with Android Studio, Android SDK, Java, and a configured emulator/device, the Android fixture can also be built and run locally. Use the commands generated by the selected React Native CLI template, typically:

```powershell
cd .\react-native-fixture
npx react-native start
npx react-native run-android
```

Keep Metro running in its own terminal when using the development build. Also perform a release Android build so validation does not depend solely on the development bundler/runtime path.

### iOS and device-dependent checks

- Building the iOS native app requires macOS and Xcode; it cannot be validated on Windows.
- Run the fixture on an iOS simulator and, where practical, a physical iOS device. Use the matching React Native CLI command, typically `npx react-native run-ios`, from macOS.
- Run Android on an emulator and at least one physical Android device when possible. Device networking, cookie storage, and cancellation behavior can differ from emulators.
- Run release Hermes builds on both iOS and Android. Do not report a platform as validated when only Node/Vitest, a web preview, Metro bundling, or the other platform passed.
- Make the HTTPS service reachable from each target device. Document certificate and network configuration; do not silently disable certificate validation.

## Execution and reporting sequence

1. Confirm the React Native minimum policy (0.86 for wider coverage or 0.87 for an active-support floor) and pin a current comparison version.
2. Reconcile package/lock metadata and ensure the tarball contains the intended public build without compiled tests.
3. Create the bare Hermes fixture and capture dependency versions and native toolchain versions.
4. Verify package-root import and development/release Metro bundles on the minimum and current versions.
5. Run the test matrix on Android and iOS, including cookie isolation and token redirect checks before enabling cache/deduplication assumptions for native consumers.
6. Investigate failures with the smallest reproducible endpoint and retain platform logs; implement fixes only after behavior is demonstrated.
7. Report exact React Native, Hermes, Metro, OS, device/simulator, and build-mode versions alongside each result. Distinguish tested behavior, known failures, and untested risks.

No native validation has been performed yet. The Node/Vitest suite remains valuable for deterministic library tests but cannot establish React Native fetch, cookie, redirect, abort, stream, Hermes-global, or Metro behavior.
